# k8s v1.33.4 对 CoreDNS 版本要求的调研报告

> 调研对象：QKE（青云 Kubernetes 引擎）集群从 k8s v1.27.10 升级到 **v1.33.4**（离线环境），当前 CoreDNS 为 **1.9.2**（QKE 3.3.0 实例），升级后实测仍为 1.9.x。
> 调研日期：基于 k8s v1.33.0 官方源码 / 官方文档 / 官方配套组件记录。

---

## 1. 结论

**k8s v1.33.4 并不"硬性要求"把 CoreDNS 升级到 v1.12.0 —— 官方没有发布任何"CoreDNS 最低版本要求"或"1.9.x 不兼容"的声明。**

但结论需要分两层说清楚：

| 判断维度 | 结论 |
|---|---|
| k8s 官方是否**强制要求** coredns ≥ 某版本 | **否**。k8s 1.33 没有任何 coredns 最低版本要求；coredns 是 addon，k8s 控制面不校验其版本 |
| k8s 官方工具（kubeadm）在 1.33 中**默认安装/升级**的 coredns | **v1.12.0**（`CoreDNSVersion = "v1.12.0"`，见证据 1） |
| kubeadm upgrade 时是否**自动**把 coredns 升到 v1.12.0 | **是**（addon 阶段默认执行，见证据 4）——但 QKE 不走 kubeadm，此行为不适用 |
| coredns 1.9.2 在 k8s 1.33.4 下**是否可用** | **基本可用**（其 kubernetes 插件在 ≥1.19 集群上监听 v1 EndpointSlice，1.33 仍提供该 API，见证据 5） |
| 是否**建议**升级到 v1.12.0 | **强烈建议**（官方配套/测试版本，且 1.9.2 已 3 年多未更新，见风险分析） |

**一句话结论：不是"必须"，但属于"强烈建议"。** 若 QKE 升级流程不自动升级 coredns，1.9.x 在 1.33.4 下大概率能继续工作，但不在 k8s 1.33 的官方配套/测试范围内，存在功能与安全风险，建议尽快升级到 **v1.12.0**（k8s 1.33 的官方配套版本）。

---

## 2. 证据

### 证据 1：kubeadm 源码 `constants.go`（v1.33.0 分支）

`cmd/kubeadm/app/constants/constants.go` 中：

```go
// CoreDNSVersion is the version of CoreDNS to be deployed if it is used
CoreDNSVersion = "v1.12.0"
```

来源：[kubernetes/kubernetes v1.33.0 `cmd/kubeadm/app/constants/constants.go`](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.33.0/cmd/kubeadm/app/constants/constants.go)

这是 kubeadm 在 k8s 1.33 中默认安装/升级的 coredns 版本，与 kubekey 文档一致。

### 证据 2：k8s v1.33 CHANGELOG

v1.33.0 正式版 changelog 明确记录：

> **v1.33.0** — Other (Cleanup or Flake)：
> "Changed the dependency version for CoreDNS. Kubernetes tools now install CoreDNS `v1.12.0`."（[#128926](https://github.com/kubernetes/kubernetes/pull/128926)，SIG Cloud Provider and Cluster Lifecycle）

> **v1.33.0-alpha.1** — "Upgrade CoreDNS to v1.12.0"（[#128926](https://github.com/kubernetes/kubernetes/pull/128926)）

来源：[kubernetes/kubernetes CHANGELOG-1.33.md](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.33.md)（v1.33.0 与 v1.33.0-alpha.1 章节）

注意：changelog 中**没有任何**"旧版 coredns 不兼容 / 必须升级"的说明，只有"默认安装版本改为 v1.12.0"这一事实性记录。

### 证据 3：CoreDNS 官方配套版本记录（coredns/deployment）

[CoreDNS version in Kubernetes](https://github.com/coredns/deployment/blob/master/kubernetes/CoreDNS-k8s_version.md) 记录 kubeadm 随各 k8s 版本安装的 coredns：

| Kubernetes | CoreDNS（kubeadm 安装） |
|---|---|
| v1.33 | **v1.12.0** |
| v1.32 | v1.11.3 |
| v1.31 | v1.11.3 |
| v1.30 | v1.11.1 |
| v1.29 | v1.11.1 |
| v1.28 | v1.10.1 |
| v1.27 | v1.10.1 |
| v1.26 | v1.9.3 |
| v1.25 | v1.9.3 |

**重要限定**：该表开头明确声明 *"This table should not be read as a recommendation for what version of CoreDNS to currently use per each Kubernetes release"* —— 即这是"kubeadm 装了什么"的**事实记录**，**不是**兼容性矩阵，**不能**据此断言"1.9.x 在 1.33 上不受支持"。

### 证据 4：kubeadm upgrade 对 coredns 的处理（v1.33.0 源码）

- `kubeadm upgrade apply` 的默认 phase 列表包含 `commonphases.NewAddonPhase()`（[apply.go](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.33.0/cmd/kubeadm/app/cmd/upgrade/apply.go)），addon 阶段含 `coredns` 子阶段（[addons.go](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.33.0/cmd/kubeadm/app/cmd/phases/upgrade/addons.go)）。
- coredns 子阶段调用 `dnsaddon.EnsureDNSAddon`，其中对 CoreDNS Deployment 使用 `apiclient.CreateOrUpdate`（[dns.go](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.33.0/cmd/kubeadm/app/phases/addons/dns/dns.go)）——即**直接更新 Deployment 镜像到目标版本 v1.12.0**，并自动用 corefile-migration 迁移 Corefile。

**结论**：kubeadm 升级时**不会报错**，而是**自动把 coredns 升级到 v1.12.0**（除非 `--skip-phases=addon` 或显式禁用 DNS）。**但 QKE 是托管引擎，不走 kubeadm，因此该自动升级行为对 QKE 不适用**——这正是 QKE 升级后 coredns 仍为 1.9.x 的原因。

### 证据 5：coredns 1.9.2 与 k8s 1.33 的 API 兼容性（源码分析）

CoreDNS 1.9.2（2022-05-13 发布，[release notes](https://github.com/coredns/coredns/blob/master/notes/coredns-1.9.2.md)）的 kubernetes 插件：

- 使用 client-go / k8s.io/api **v0.24.0**（[go.mod](https://raw.githubusercontent.com/coredns/coredns/v1.9.2/go.mod)）。
- 启动时 `endpointSliceSupported()` 逻辑（[kubernetes.go](https://raw.githubusercontent.com/coredns/coredns/v1.9.2/plugin/kubernetes/kubernetes.go)）：k8s ≥ 1.19 时优先探测 `discovery/v1` EndpointSlice，存在则监听 **v1 EndpointSlice**；仅当 v1 不存在才回退 v1beta1 / 旧 Endpoints。
- k8s 1.33 仍提供 `discovery/v1` EndpointSlice（GA 于 1.21，未移除），因此 **coredns 1.9.2 在 1.33.4 上会监听 v1 EndpointSlice，基础服务发现（Service/Headless/Endpoint 解析）可正常工作**。

**没有找到任何官方声明说 coredns 1.9.x 在 k8s 1.33 上"不可用/不受支持"。**

### 证据 6：kubekey 官方文档（用户提供，已核实）

[kubekey components.md](https://raw.githubusercontent.com/kubesphere/kubekey/faf2739a7b4ed03f282fd0ef38479e35a49e0340/docs/en/installation/components.md) 中 coredns 表：

| kubernetes version | recommended coredns | kubekey default |
|---|---|---|
| 1.27~1.28 | v1.10.1 | v1.10.1 |
| 1.29 | v1.11.1 | v1.11.1 |
| 1.30~1.32 | v1.11.3 | v1.11.3 |
| **1.33.0~1.33.7** | **v1.12.0** | **v1.12.0** |

与 kubeadm 常量、coredns/deployment 记录三方一致。

## 3. 风险分析（若保持 coredns 1.9.x 在 k8s 1.33.4 下运行）

1. **不在官方配套/测试范围内（最主要风险）**：k8s 1.33 的官方配套 coredns 是 v1.12.0。1.9.2 发布于 2022-05，比 1.33（2025-04）早约 3 年，未针对 1.33 做过验证。虽然基础功能可用，但属于"未验证组合"。

2. **旧版 coredns 因 API 变更失效的已知先例**：华为云 CCE 官方 FAQ 记录了真实案例——旧版 coredns（1.8.4）在集群升级后仍监听被移除的 `v1beta1.EndpointSlice`，导致**新建 Service 域名无法解析、Headless Service 返回旧 Pod IP**（[华为云 CCE FAQ：如何解决CoreDNS使用废弃API问题](https://support.huaweicloud.com/cce_faq/cce_faq_00490.html)）。coredns 1.9.2 在 ≥1.19 集群上监听 v1 EndpointSlice，**当前不受此问题影响**，但该案例说明"旧 coredns + 新 k8s"存在此类 API 演进风险，需在升级后验证 DNS。

3. **功能缺失**：1.9.x 缺少 1.10/1.11/1.12 中新增的 kubernetes 插件能力（如 client 级 apiserver 指标、`client-label` metadata 等），且 1.9.2 的 client-go v0.24 对 1.33 新增的 API 字段/行为不感知。

4. **安全与稳定性**：1.9.2 之后有大量安全修复（如 cache 投毒修复等，见 [1.9.2 release notes](https://github.com/coredns/coredns/blob/master/notes/coredns-1.9.2.md) 及后续版本）；1.9.2 已停止维护，长期运行存在已知/未知漏洞风险。

5. **kubeadm 升级报错风险（仅对 kubeadm 集群）**：若集群是 kubeadm 管理，`kubeadm upgrade apply` 会**自动**把 coredns 升到 v1.12.0，不会报错；但若离线环境缺少 v1.12.0 镜像，addon 阶段会因**拉取镜像失败**而中断升级（`PullImage` 失败）。**QKE 不走 kubeadm，此条不适用，但离线环境需提前备好 v1.12.0 镜像。**

6. **无法确认项**：QKE 官方是否将 coredns 1.9.x 列为 k8s 1.33.4 的受支持组合，属于 QKE 私有兼容性声明，公开资料无法确认，需查 QKE 官方兼容性文档或咨询青云。

---

## 4. 建议

1. **升级到 v1.12.0（推荐）**：这是 k8s 1.33 的官方配套版本（kubeadm 常量、coredns/deployment 记录、kubekey 三方一致）。离线环境请提前将 `coredns/coredns:v1.12.0` 镜像导入私有仓库，并保留现有 Corefile（1.9.x → 1.12.0 的 Corefile 迁移由 corefile-migration 支持，kubeadm 会自动处理；QKE 手动升级时需自行核对 Corefile 兼容性）。

2. **若短期无法升级**：coredns 1.9.x 在 1.33.4 下**基本可用**，可继续运行，但必须：
   - 升级后**验证 DNS**：新建 Service 域名解析、Headless Service 变更后解析、`kubectl run` 内解析、coredns 日志无 `Failed to watch ... EndpointSlice` 类告警；
   - 关注 coredns 日志中是否有对已移除 API 的 watch 失败（参考华为云 FAQ 的排查方法）；
   - 制定升级到 v1.12.0 的后续计划。

3. **不要仅凭"kubeadm 默认 v1.12.0"就断言"必须升级"**：k8s 官方没有 coredns 最低版本要求，1.9.x 未被官方声明为不兼容；"必须"的说法缺乏依据，准确表述是"官方配套版本为 v1.12.0，强烈建议升级"。
